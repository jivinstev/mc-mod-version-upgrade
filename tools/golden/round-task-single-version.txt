Run the keep-current skill's weekly round for this fork set, unattended (fresh session, no human present).

The fork set's only source is .github/weekly-plan.json on o/lib branch neoforge-1.21.1 (no fleet file). As setup wrote it (dependency order, the library first; the plan issue is on the first):
- o/lib head neoforge-1.21.1 (library); authors' upstream https://github.com/a/lib main; ledger issues none; automerge no
- o/dep head neoforge-1.21.1 (dependent); authors' upstream https://github.com/a/dep.git dev; depends on o/lib; ledger issues none; automerge no

Unattended permissions (the `allow` list in the config, chosen by the owner at setup; exactly these, nothing more):
- none: every push (the round's work branches included), PR, pre-release and merge needs the owner's answer first.
Always allowed, whatever the list says, because they are how the round reports: comments on the plan issue (and closing it at the close), and edits to the ledger issues listed above.
Nothing on the migrator repository, apart from reading it (the clone in step 1), is ever allowed.
Any other action is a stop: do not take it; ask the owner in a comment on the plan issue (@mention them, the action and why), go on with what the list allows, and report it at the close.

Steps:
1. git clone --depth 1 https://github.com/owner/migrator mmvu (public, read only; never ask for it to be attached) and read mmvu/.claude/skills/keep-current/SKILL.md, section "The weekly round". Follow it exactly, in order. This is the migrator's current main, on purpose: the round runs the newest tools and skill, fixes included. Tuesday's plan workflow ran the tools pinned at `migrator_sha` in .github/weekly-plan.json, so that a plan is reproducible from its commit; the two meet only at the plan issue, which step 3 reads. If read-plan cannot read it, stop and report (setup must be re-run to move the pin).
2. First of all, before freezing anything: python3 mmvu/tools/round-preflight.py --fork o/lib=<its clone> --fork o/dep=<its clone>. A fork with no clone in this session: stop now -- this scheduled session cannot attach a repository (add_repo is refused here), so post one comment on the newest open plan issue on o/lib naming the repository and saying it must be added to this scheduled task's repositories, and stop. Install or set what else it names that the session can (a JDK, libegl1, XDG_RUNTIME_DIR) and run it again. Read .github/weekly-plan.json from o/lib's neoforge-1.21.1: if it differs from the fork set above, stop and report that setup must be re-run. GitHub is read through GITHUB_TOKEN when it is set (over REST; a broken gh login then does not matter), else GH_TOKEN, else gh.
3. Freeze the input: python3 mmvu/tools/known-issues.py read-plan --latest --slug o/lib --out round/frozen.json --decisions-dir round/decisions. The selected known issues and the authors' changes it says to take are the run's only inputs; nothing else enters except a new S1. With no open plan issue, stop and report. Each fork's `dep_bumps` there are the dependency updates the owner left ticked: apply each exactly once, at that version's setup and before its gates, by its `command` (layer-deps.py resolve --bump, in the checkout of that version's branch), and commit it; no other step moves a dependency (every resolve keeps the pins), and an unticked one stays as it is.
4. A fork with version branches (.port/<v>/branch.properties) is a version-branch fork even when a legacy layer branch with .multiversion/ exists: that layer branch is history; ignore it.
5. Never promote a release, publish to Modrinth or CurseForge, push to or comment on the authors' repositories, force-push, or merge into the migrator repository.
6. A round that stops before its close leaves the plan issue open (next Tuesday's plan carries it forward); only the closing comment of a round that ran its steps closes it.
7. Keep this session small: it orchestrates and never does a version's porting, gating or review in its own context. Each version's fixer and reviewer are fresh subagents that return a short summary (at most ~40 lines: what changed, gate verdicts, open rows, commit shas); keep only those, never their transcripts or the build logs. One worker may carry the same change across several versions (a re-pin, one fix cascaded up) while its context stays modest; distinct porting work at each version gets a fresh worker per version. Wait for gates and CI in ONE blocking command (`gh run watch <run id> --exit-status`, or a single until-loop run in the background or under Monitor), never by polling turn by turn: every idle gap longer than 5 minutes re-writes this session's whole cached context, so a small context and few, long waits are what keep the round cheap. If this session's context passes ~200k tokens, write the round's state (frozen input, per-version status, open rows, shas, what comes next) to round/NOTES.md and continue from a fresh subagent that reads it.
8. Mark each change of the kind of work with python3 mmvu/tools/port-cost.py mark --fork <owner/repo> --version <v> --phase upstream|backlog|review|overhead (upstream: the authors' cascade and its conflicts; backlog: the selected known-issue fixes; review: fresh reviews and the fixes they cause; overhead: pins, gates, CI waits, records). The closing comment's cost table (round-table --session-cwd) gives the per-phase split and per-phase totals, and for upstream the size of what the authors changed per version (commits, files, changed lines) and how many files the cascade merged mechanically versus by an agent, so cost per authors' changed line and the mechanical-merge share can be compared week over week.
9. Before closing, the closing comment carries a `### Lessons for the migrator` table (every fork kind, single-version included; text only): | version | symptom | fork commit | why it looks general |, one row per candidate lesson whose cause looks like the version, NeoForge, a library or a shared helper rather than the mod -- the error text or behaviour, the fix as owner/repo@<sha> -- or one `| none | | | |` row.
