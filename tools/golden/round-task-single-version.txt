Run the keep-current skill's weekly round for this fork set, unattended (fresh session, no human present).

- o/dep head neoforge-1.21.1 (dependent); authors' upstream https://github.com/a/dep.git dev; depends on o/lib; ledger issues none; automerge no

Unattended permissions (the `allow` list in the config, chosen by the owner at setup; exactly these, nothing more):

Always allowed, whatever the list says, because they are how the round reports: comments on the plan issue (and closing it at the close), and edits to the ledger issues listed above.
Nothing on the migrator repository, apart from reading it (the clone in step 1), is ever allowed.
Any other action is a stop: do not take it; ask the owner in a comment on the plan issue (@mention them, the action and why), go on with what the list allows, and report it at the close.

Steps:
1. git clone --depth 1 https://github.com/owner/migrator mmvu (public, read only; never ask for it to be attached) and read mmvu/.claude/skills/keep-current/SKILL.md, section "The weekly round". Tuesday's plan workflow ran the tools pinned at `migrator_sha` in .github/weekly-plan.json, so that a plan is reproducible from its commit; the two meet only at the plan issue, which step 3 reads. If read-plan cannot read it, stop and report (setup must be re-run to move the pin).
2. First of all, before freezing anything: python3 mmvu/tools/round-preflight.py --fork o/lib=<its clone> --fork o/dep=<its clone>. A fork with no clone in this session: stop now -- this scheduled session cannot attach a repository (add_repo is refused here), so post one comment on the newest open plan issue on o/lib naming the repository and saying it must be added to this scheduled task's repositories, and stop. Install or set what else it names that the session can (a JDK, libegl1, XDG_RUNTIME_DIR) and run it again. Read .github/weekly-plan.json from o/lib's neoforge-1.21.1: if it differs from the fork set above, stop and report that setup must be re-run. 3. Freeze the input: python3 mmvu/tools/known-issues.py read-plan --latest --slug o/lib --out round/frozen.json --decisions-dir round/decisions. The selected known issues and the authors' changes it says to take are the run's only inputs; nothing else enters except a new S1. With no open plan issue, stop and report. Each fork's `dep_bumps` there are the dependency updates the owner left ticked: the driver (rule 7) applies each exactly once, at that version's setup and before its gates, by its `command` (layer-deps.py resolve --bump, in the checkout of that version's branch), and commits it; no other step moves a dependency (every resolve keeps the pins), and an unticked one stays as it is.
4. A fork with version branches (.port/<v>/branch.properties) is a version-branch fork even when a legacy layer branch with .multiversion/ exists: that layer branch is history; ignore it.
5. Never promote a release, publish to Modrinth or CurseForge, push to or comment on the authors' repositories, force-push, or merge into the migrator repository.
6. A round that stops before its close leaves the plan issue open (next Tuesday's plan carries it forward); only the closing comment of a round that ran its steps closes it.
7. Run the round with its driver and never do a step by hand. Right after step 3: python3 mmvu/tools/round.py init --frozen round/frozen.json --fork <owner/repo>=<its clone> for every fork, the library first. Then run python3 mmvu/tools/round.py drive --follow > round/drive.out 2>&1 in the background and watch round/drive.out with ONE Monitor for lines starting `round: AGENT JOB `, `round: BLOCKED` or `round: ROUND DONE` (the driver runs every mechanical step itself -- merge-ups one version at a time, re-pins, gates, the library's pre-merge dependent gate, PRs, CI waits, merges, release dispatch, records, phase marks -- versions overlapping, and blocks in its own waits). For each AGENT JOB line, start a fresh background subagent whose whole prompt is the job's `prompt`; the driver records each job itself from its summary file, so when a subagent ends do nothing unless its summary file is missing -- then run the job's `record` line with --status failed. Never read a worker's transcript, its summary or a log here. drive exit 3 means blocked: its BLOCKED lines say what: handle only that, then start drive --follow again. round/STATE.json is the round's only memory: after a restart, or once this session's context passes ~100k tokens, continue from a fresh session with python3 mmvu/tools/round.py resume, then drive --follow again. Keep this session small -- the job lines and the drive output only: every idle gap longer than 5 minutes re-writes its whole cached context.
